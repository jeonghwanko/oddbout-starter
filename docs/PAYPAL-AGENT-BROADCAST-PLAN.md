# ODDBOUT Agent Broadcast — PayPal 공모전 개발 계획

작성: 2026-11-02, Asia/Seoul. 상태: **개발 진행 중**. 구현 작업이 시작됐으며, 이 상태 표시는 기능의 완료·테스트 통과·외부 연동 성공을 뜻하지 않는다.

기준 저장소: oddbout-starter 최신 main `d84baee7`. 이 계획의 API/MCP 도구명과 신규 경로는 코드에서 실제 제공될 때까지 모두 제안이다.

현재 구현·실행법·검증 기록은 [BROADCAST-SANDBOX](BROADCAST-SANDBOX.md), 방송 설정은 [NIGHTCROWN-BROADCAST-CONCEPT](NIGHTCROWN-BROADCAST-CONCEPT.md)를 따른다. Sandbox 결제 어댑터·원장·예산·MCP·호스트 선택 실행기와 별도 Cup 렌더러를 구현했다. 실제 PayPal 거래, Twitch 송출, 24시간 운전은 미검증이며 `--live`는 아직 구현되지 않은 채널 검증 때문에 차단된다. 아래 목표·일정을 완료 기록으로 해석하지 않는다.

사용자가 승인한 제품 방향은 PayPal 결제로 ODDBOUT 재화를 충전하고, 에이전트가 그 재화를 사용해 최소 네 캐릭터의 대회를 편성·송출하며, 24시간 운영 뒤 리포트를 제공하는 것이다. 이 문서는 구현 범위·책임 경계·검증 조건을 정한다. 문서 작성은 실결제·실제 방송·캐릭터 생성·운영 배포를 실행하지 않는다.

공식 마감은 2026-11-12 12:00 PST, **한국 시간 2026-11-13 05:00**이다. 내부 제출 목표는 **11월 12일 18:00 KST**로 둔다. 일정은 목표이며 완료 기록이 아니다. 공식 출처는 마지막 절에 있다.

## 1. 제품과 심사에서 보여줄 가치

> PayPal로 방송 예산을 충전하면, AI 프로듀서가 캐릭터를 섭외하고 대회를 편성해 24시간 방송한 뒤 지출과 운영 결과를 보고한다.

초기 고객 가설은 ODDBOUT 캐릭터 소유자와 반복 대회 방송을 운영하고 싶은 소규모 방송자다. 사람이 계속 대진을 짜고 경기를 재시작하고 비용을 정리하는 부담을 줄인다. 이 가설의 지불 의향은 아직 검증되지 않았다. 출시 전 대상 사용자 3명 이상에게 실제 편성·가격 화면을 보여주고, 맡기고 싶은 작업과 거절 이유를 기록한다. 인터뷰를 매출이나 실제 이용 성과로 표시하지 않는다.

PayPal은 충전의 결제 수단이고, MCP 작업은 서버 원장에 기록된 재화를 사용한다. **각 MCP 호출이 PayPal 현금 결제를 발생시키는 구조로 설명하지 않는다.** 에이전트의 반복적인 승인창 없이, 사용자가 승인한 채널·기간·예산 안에서 유료 작업을 수행한다.

핵심 시연은 다음 두 가지다.

- 에이전트가 잔액·가격·운영 목표를 읽고, 신규 생성과 기존 선수 활용 중 비용에 맞는 편성을 선택한다.
- PayPal 결제 한 건에서 충전, 작업별 지출, 실제 송출, 최종 리포트까지 추적한다. 실패·재시도로 추가 청구되지 않음을 보여준다.

주요 적합 부문은 Best Use of Agentic Commerce, 보조 부문은 Best Demo Delivery다. 수상 가능성이나 참가자 수를 확정 경쟁률로 표현하지 않는다.

## 2. 저장소 결정

**주 개발 및 제출 안내의 기준 저장소는 oddbout-starter로 한다. oddbout-twitch-cup은 전투 실행·방송 화면을 담당한다.** 두 저장소를 합치거나 새 저장소를 만드는 작업은 이번 범위에 포함하지 않는다.

| 책임 | 저장소 | 근거와 방향 |
| --- | --- | --- |
| 로그인·계정, PayPal, 재화 원장, 예산 승인 | oddbout-starter | 기존 api, Supabase Auth·마이그레이션 경계 활용 |
| 유료 MCP, AI 편성, 작업 예약·리포트 | oddbout-starter | 기존 호스팅 MCP와 서버 작업 모델 활용 |
| 송출 실행기, OBS 제어, 실행 복구 | oddbout-starter | 기존 검증 worker와 분리된 프로세스 추가 |

확인 기준: starter main bbeaac9c, Twitch Cup 1535650c17eb9f531dbcfe2d1ea635eba3088325. 이는 계획 작성 시점의 조사 기준이며 최종 제출 버전이 아니다.

starter에는 이미 [API handler](../api/handler.mjs), [호스팅 MCP](../mcp/cloud.mjs), [클라우드 도구](../mcp/cloud/), [생성 API](../api/generations.mjs), [worker](../worker/), [DB migrations](../supabase/migrations/), MIT [LICENSE](../LICENSE)가 있다. 이름이 starter여도 현재 책임 범위는 제작 키트에 한정되지 않는다.

중요한 기존 경계:

- starter의 기존 사이트 빌드와 운영 전투 엔진 배포는 별도 게임 저장소에 의존한다. 이 저장소의 운영 duel adapter를 완성된 엔진으로 간주하지 않는다.
- 기존 ai-fighter Edge 배포를 이 checkout에서 직접 실행하지 않는다. [AGENTS](../AGENTS.md)와 [CREATOR-HOSTING](CREATOR-HOSTING.md)의 기존 배포 경로를 유지한다.
- 해커톤용 웹·API·MCP 실행 진입점은 공개 소스만으로 실행되도록 별도로 조립한다. 기존 비공개 게임 사이트 빌더를 필수 의존성으로 두지 않는다.
- Twitch Cup에는 현재 프로젝트 라이선스가 없다. 재사용 코드·에셋에 대한 공개 라이선스 범위를 소유자가 결정하고 NOTICE를 검토하는 것이 첫 단계의 완료 조건이다. starter의 MIT가 다른 저장소의 코드·에셋에 자동 적용되지 않는다.
- 두 저장소의 소스 SHA와 실행 계약 버전을 제출 manifest에 고정한다. 공개 저장소 두 곳의 설치 순서·의존성을 하나의 제출 README에서 설명한다.
- 공유 main checkout은 전환하지 않는다. 저장소별 codex/paypal-* worktree에서 변경하고, 파일을 명시해 커밋한다. 이 계획의 브랜치는 codex/paypal-agent-broadcast-plan이다.
- 개발·실행 호스트는 사용자가 선택한다: 현재 PC(Windows), office-stable(Linux), svl-mac-01(macOS). 호스트 이름만으로 접근 권한이나 준비 상태를 가정하지 않는다. 각 호스트에서 checkout·설치 위치·실행 계정을 확인하고, 선택한 호스트에만 필요한 연결을 수행한다.

## 3. 범위와 완료 기준

### P0 — 공모전 핵심 경로

- PayPal Sandbox 주문 생성·사용자 승인·capture 검증·정확히 한 번 충전.
- 잔액, 사용 가능 재화, 방송에 예약된 재화, 작업별 내역을 확인하는 화면.
- 사용자가 채널 하나·기간·지출 한도·허용 도구를 승인하는 방송 예산.
- 공개 사용 가능한 기존 캐릭터 네 명으로 무인 대회 편성. 필요한 실행 모드는 시청자 참가 모드와 명시적으로 구분한다.
- 실제 모델이 MCP를 호출해 계획과 유료 작업을 선택하는 에이전트. 고정 응답 재생은 AI 구현 검증으로 인정하지 않는다.
- 컵 반복 실행, 실제 Twitch 송출, 장애 감지·복구, 예산/종료시각/사용자 중지 처리.
- 서버 기록에 근거한 비용·대회·방송 상태 리포트.
- 실시간 단기 데모와 별도의 24시간 운전 증거. 24시간 검증 실패는 해당 완료 조건 미충족으로 기록한다.
- 공개 소스·라이선스·영문 실행 안내·3분 미만 공개 YouTube 영상.

### P1 — 핵심 경로 통과 후

- 신규 캐릭터 한 명 생성 후 기존 세 명과 편성하는 추가 시연.
- 주요 장면의 시각·경기 링크를 포함하는 리포트와 편성 다양화.
- 기존 데이터를 실제로 수집할 수 있을 때만 시청자 반응에 따른 다음 대회 편성.

현재 계정당 선수 등록 세 명 제한과 제작 과정의 외형·모션 검토·등록 승인을 유지한다. 방송 위임을 캐릭터 제작 검토 전체의 포괄 위임으로 해석하지 않는다. 신규 제작이 검토 대기 또는 한도 초과이면 기존 선수로 계속할 수 있도록 계획한다. 기존 무료 생성·제한 정책을 유료 호출 때문에 임의로 우회하지 않는다.

### 이번 제출에서 제외

실거래 과금, 자동 현금 재충전, 재화 송금·현금화, 베팅·상금 분배, 여러 채널 동시 운영, 모든 MCP 클라이언트 지원, 신규 캐릭터 네 명의 무인 제작, 실시간 음성 해설, 자동 영상 편집·업로드, 기존 사이트 전체 개편. HTTP 402/x402 구현은 필수 기능이 아니다.

## 4. 사용자 흐름과 화면

1. ODDBOUT 로그인 후 방송 콘솔에서 PayPal Sandbox로 재화를 충전한다. 검증 중·실패·취소를 성공과 구분한다.
2. 사용자가 연결한 Twitch 채널, 목표 종료시각, 예산, 허용 캐릭터·도구를 지정한다.
3. 에이전트가 편성과 비용 견적을 제시한다. 실제 금액·재화 환산율·도구 가격은 서버 가격표에서 가져온다.
4. 사용자가 신뢰된 콘솔에서 예산을 승인한다. 승인 기록은 계정·채널·기간·한도·도구·가격표 버전에 결합된다.
5. 에이전트가 승인된 예산으로 실행한다. 콘솔에 현재 컵·송출 상태·예약/확정 지출·남은 시간·다음 계획을 표시한다.
6. 재화가 부족하면 신규 작업을 시작하지 않고 예산 소진으로 종료한다. 사용자가 새로 승인하지 않은 현금 충전은 없다.
7. 종료·취소·실패 모두 리포트를 남긴다. 미사용 예약 재화는 반환하고 이미 완료된 유료 작업은 내역에 남긴다.

화면은 잔액/충전, 방송 계획/승인, 운영 상태/중지, 종료 리포트의 네 영역으로 제한한다. 공개 방송 화면에는 파이터·대진·챔피언을 표시하고, 개인 잔액·주문 ID·계정 정보는 운영자 콘솔에만 표시한다.

## 5. 실행 구조

~~~mermaid
flowchart LR
    U[사용자 콘솔] --> P[PayPal Sandbox]
    P --> C[결제 검증 API]
    C --> D[(재화 원장 / 작업 DB)]
    U --> B[예산 승인]
    B --> D
    A[AI 프로듀서] --> M[호스팅 MCP]
    M --> S[견적 / 예산 / 작업 서비스]
    S --> D
    D --> W[방송 실행기]
    W --> G[Twitch Cup 브라우저]
    W --> O[OBS / 인코더]
    G --> O
    O --> T[Twitch]
    W --> D
    D --> R[운영 리포트]
    R --> U
~~~

에이전트는 계획과 다음 작업을 결정한다. 항상 켜진 별도 프로세스가 영속 작업을 실행한다. 대화창을 닫아도 예약 작업과 송출은 유지되고, 새 대화에서는 같은 broadcastId로 상태를 조회한다. 모델을 매 프레임 또는 짧은 heartbeat마다 호출하지 않는다.

### starter의 추가 모듈 배치안

아래 신규 경로와 명령은 제안이며 아직 존재하지 않는다. 기존 모듈의 인터페이스에 맞춰 구현 시 세분화한다.

| 제안 경로 (아직 미구현) | 책임 |
| --- | --- |
| api/commerce/ | PayPal adapter, 가격표, 충전, 원장·예약 서비스, webhook |
| api/broadcast/ | 예산 승인, 방송/컵 작업, 실행기 lease, 결과 접수, 리포트 |
| mcp/cloud/commerce-tools.mjs | 잔액·견적·결제 승인 링크·지출 조회 |
| mcp/cloud/broadcast-tools.mjs | 방송 시작/상태/중지, 대회 작업, 리포트 |
| broadcast/producer.mjs | 선택한 모델 provider adapter와 영속 의사결정 루프 |
| broadcast/runner.mjs | 브라우저·OBS·작업 lease·복구·계측; 기존 validator와 별도 실행 |
| web/broadcast/ | 비공개 게임 소스에 의존하지 않는 콘솔 |
| supabase/migrations/ | commerce/broadcast 테이블·원자적 상태 전이; 기존 prefix 관례 적용 |
| scripts/broadcast-demo.mjs | 공개 두 저장소를 지정한 SHA로 실행하는 데모 진입점 |
| test/commerce-*.test.mjs, test/broadcast-*.test.mjs | 외부 결제·송출 경계와 실제 내부 규칙 검사 |

새 서버 모듈도 기존 ESM JavaScript + JSDoc + strict typecheck 관례를 따른다. Node는 두 저장소를 만족하는 22 계열을 사용한다. 기존 검증 worker를 24시간 영상 렌더링 프로세스로 전환하지 않는다. 해커톤 환경의 API·DB·자격증명과 운영 환경은 구분한다.

호스트 선택은 실행 설정에 명시적으로 저장하고, 인증된 사용자 계정과 선택한 호스트 연결을 서버에서 결합한다. 에이전트가 요청 인자로 호스트 소유자나 권한을 지정할 수 없어야 한다. 호스트마다 별도 capability doctor가 OS·필수 프로그램·버전·실행 권한·선택된 checkout과 로컬 서비스 접근을 검사하고, 통과하지 못하면 해당 호스트에서 송출을 시작하지 않는다. 검사 출력에는 자격증명이나 `.env` 값을 포함하지 않는다. `current-pc` Windows, `office-stable` Linux, `svl-mac-01` macOS의 실제 설치·접근 가능성은 각 호스트에서 관찰 전까지 미확인이다.

### Twitch Cup 변경 경계

- 기존 src/app, src/platform, src/render/boot, src/sim의 책임을 보존한다. 결제·원장을 전투 상태 규칙에 넣지 않는다.
- 제어용 별도 방송 진입점과 adapter를 추가한다. 시청자 !join 경로에 가짜 Twitch 사용자 네 명을 넣어 자동 편성을 구현하지 않는다.
- 방송 모드는 승인된 실행기만 제어한다. 네 선수의 고유성, 준결승 두 경기와 결승, 활성 경기 결과만 반영하는 규칙을 재사용한다.
- 제어 계약에 protocolVersion, broadcastId, cupId, jobId, lease generation, boutId, 선수/패키지 버전, engine/source 버전, seed, 결과 digest를 둔다.
- 기존 iframe의 origin/source/경기 ID/선수/seed 검증은 계속 적용한다. ready/error는 승리가 아니다.
- 사용자 브라우저가 보내는 임의 결과로 과금을 확정하지 않는다. 승인된 실행기가 현재 lease로 제출한 결과와 서버 작업을 대조한다.
- 난수 소비 순서·고정 시뮬레이션 스텝·240초 watchdog은 이 기능을 이유로 변경하지 않는다.

## 6. 결제·재화·예산 계약

### 충전

서버 가격표의 충전 상품을 선택해 주문을 만들고, 사용자 승인 뒤 서버에서 capture 결과를 확인한다. capture의 COMPLETED 상태, 주문 연결, 금액·통화·수취인·Sandbox 환경·소유 계정을 검증한다. 승인 페이지 복귀나 URL 파라미터만으로 충전하지 않는다.

PayPal-Request-Id는 API 종류별로 안정적인 키를 사용한다. capture 결과가 불명확하면 같은 주문을 조회·조정하고 새 결제 주문을 자동 생성하지 않는다. 서명 검증된 webhook과 동기 capture 응답은 같은 충전 함수를 호출한다. capture ID의 고유 제약과 DB 트랜잭션으로 한 번만 충전한다. webhook은 재전송·역순 도착을 처리하고, 영속 수신 전 성공 응답으로 이벤트를 버리지 않는다.

금액은 통화의 최소 단위 정수, 재화는 정수로 저장한다. Sandbox 재화는 기존 게임의 gold·무료 quota와 합치지 않는다. 전환율과 가격은 운영 확정 전까지 데모 가격으로 명시한다.

### 예약과 확정

- 승인된 방송을 시작할 때 예산 한도만큼 계정 재화를 세션에 예약한다. 잔액과 예산을 한 트랜잭션에서 검사한다.
- 컵/송출 작업의 예약은 그 세션 예약액 내부에서 배분한다. 계정에서 같은 금액을 두 번 예약하지 않는다.
- 작업 성공 시 계정 잔액과 세션 예약액을 같은 금액만큼 줄여 지출을 확정한다. 실패가 확인되면 작업 배분을 해제한다.
- 결과 불명확 상태는 실패로 간주해 즉시 반환하거나 다시 실행하지 않는다. 원래 작업을 조회하고 lease·결과와 대조한다.
- 종료 시 진행 작업을 정리하고 남은 세션 예약액을 해제한다. 사용자 화면에서 확정 지출과 예약 금액을 구분한다.
- 잔액 = 확정 충전 + 지출 취소 보정 − 확정 지출 − 충전 환불 보정. 사용 가능액 = 잔액 − 열린 세션 예약 합계.
- 계정 사용 가능액은 음수가 될 수 없고, 세션의 확정 지출 + 남은 예약액은 승인 한도를 초과할 수 없다.

| 작업 | 과금 단위 및 성공 조건 |
| --- | --- |
| host_cup | 4인 컵 한 건. 세 경기와 우승 결과가 서버에 확정되면 차감; 복구 불가능한 미완주 컵은 예약 해제 |
| 송출 작업 | 고정 단가의 검증된 송출 분. 다음 구간 비용을 세션 내부에 배분하고, 겹치지 않는 완료 구간만 확정 |
| create_fighter (P1) | 견적에서 합의한 산출물의 검증·전달 한 건. 검토·등록·무료 quota 조건을 우회하지 않음 |
| 잔액, 견적, 상태, 기존 결과, 기본 종료 리포트 | 무료. polling·같은 작업의 재시도는 추가 과금 없음 |

송출 단가는 렌더링/송출 자원을, 컵 단가는 대회 실행 서비스를 포함한다고 설명한다. 포함 항목을 가격표에 명시해 이중 청구로 보이지 않게 한다. 모델·클라우드 실제 원가는 별도 운영 지표이며 데모 재화 소모량을 매출이나 이익으로 표시하지 않는다.

충전 환불과 서비스 실패에 따른 재화 예약 해제는 별개의 처리다. P0에서는 테스트 관리자의 Sandbox 미사용 충전 환불과 중복 이벤트 방어를 검증한다. 소비된 충전의 환불/취소 이벤트는 조정 필요 상태로 남기고 추가 지출을 막는다. 실제 돈의 환불 정책은 상용 출시 전 별도로 결정한다.

### 데이터 모델 초안

| 엔터티 | 핵심 정보·불변 조건 |
| --- | --- |
| 충전 주문 | owner, environment, order/capture ID, 금액/통화, 환산 재화, 상태; capture 중복 충전 금지 |
| 결제 이벤트 inbox | provider event ID, 검증 결과, 처리 상태; 중복·역순 수신 안전 |
| 지갑·원장 | owner, 재화 단위, append-only 증감 내역, 원인 ID; 수정 대신 보정 이벤트 |
| 예산 승인 | owner, channel, 시작/종료, 한도, 허용 도구/선수/단가, 승인 버전, 취소 상태 |
| 방송 세션 | 승인 ID, 초기 예약액/잔여액, 상태, source versions, 마지막 정상 상태 |
| 작업·배분 | logical idempotency key, 입력 hash, 가격 버전, 상태, lease/fence, 배분액, 결과 ID |
| 컵·경기 결과 | 선수 패키지·seed·engine/source 버전, 우승자, digest, 실행 증거; stale 결과 거부 |
| 송출 구간·리포트 | 중복되지 않는 구간 ID, encoder/Twitch 관측, 실제 제공 시간, 리포트 입력 snapshot |

테이블 노출과 RLS는 역할별로 정의한다. 사용자는 자기 잔액·방송만 읽고, 원장·충전·작업 확정은 검증된 서버만 기록한다. 계정 ID는 모델 입력이 아닌 인증에서 결정한다. 공개 schema의 테이블은 RLS와 명시적 권한을 함께 검토한다. service key·PayPal secret은 브라우저나 VITE_*에 두지 않는다. 구현 시 로컬 DB에서 동시 실행과 권한 테스트를 하고 migration을 생성·검토한다.

## 7. MCP와 실제 에이전트

도구명은 제안이다. 기존 무료 도구를 일괄 유료화하지 않고 새로운 유료 작업을 명시한다. 기존 arena read budget은 rate limit이며 구매 재화와 별개다.

| 도구 | 동작 |
| --- | --- |
| get_credit_balance / list_usage | 사용 가능액·예약액·작업 지출 조회 |
| create_topup_checkout | 서버 상품의 Sandbox 승인 링크 생성; 호출만으로 현금 결제하지 않음 |
| quote_broadcast | 채널·시간·편성·가격·부족액 계산; 승인되지 않은 초안 생성 |
| start_broadcast | 웹에서 승인된 mandate ID와 입력 hash를 대조하고 재화 예약·세션 시작 |
| host_cup | 승인 범위의 네 선수로 컵 작업 생성; 동일 논리 요청은 동일 작업 반환 |
| get_broadcast / get_job | 장시간 작업 조회·복구; 무료 |
| stop_broadcast | 신규 배분 중단, 진행 작업 정리, 송출 종료, 미사용 예약액 반환 |
| get_broadcast_report | 저장된 수치·근거와 AI 설명 조회; 조회 재시도 무료 |

모든 유료 작업은 서버 견적 ID, 입력 hash, idempotency key, 승인 ID에 연결한다. 같은 key에 다른 입력은 충돌로 거부한다. 모델이 임의 가격이나 승인 한도를 전달해 바꿀 수 없다. 잔액 부족은 구조화된 insufficient_credits와 충전 경로로 전달하며, 일반 MCP 클라이언트가 HTTP 402를 자동 처리한다고 가정하지 않는다.

결제 안내는 대상 클라이언트가 지원하면 URL elicitation을 사용하고, 그렇지 않으면 신뢰된 콘솔 링크와 명시적인 재개 호출을 사용한다. 한 개 실제 클라이언트를 G0에서 확정해 끝까지 검증한다.

24시간 운영의 AI provider adapter는 서버 실행기에 둔다. 모델·계정·비용 상한은 실행 전 설정하며 자동 provider 전환은 없다. 제어 서비스와 혼동하지 않도록 모델이 호출한 실제 MCP 요청/응답, 비용 판단, 결정 근거를 비밀값 없이 기록한다. 한 컵 종료·장애·예산 변화 같은 사건에 반응하며 모델 호출 수·최대 토큰·재시도 상한을 둔다. 모델 장애 시 이미 승인된 작업만 완료하고 새 유료 작업은 대기 또는 종료한다.

필수 에이전트 검증: 같은 방송 목표에 대해 충분한 예산, 부족한 예산, 실행기 불가 상태를 주고 실제 견적·도구 선택·설명·결과를 기록한다. 정답 문구를 고정하기보다 한도 준수와 실행 가능한 선택을 검사한다. 시청자 채팅은 편성 참고 데이터일 뿐 지출 권한이나 시스템 명령이 아니다.

## 8. 방송 실행과 24시간 운전

첫 배포 대상은 사용자가 선택한 한 대의 상시 가동 호스트와 Twitch 채널 하나다. OBS를 사용한 브라우저 캡처·RTMP 송출을 우선 검증한다. OS·GPU·OBS 설치 여부는 아직 확인하지 않았으므로 G0에서 호스트를 선정한다. 기존 생성 PC나 현재 검증 worker가 영상 송출에 적합하다고 가정하지 않는다.

- 실행기는 lease와 단조 증가하는 fence를 사용한다. lease를 잃은 이전 실행기의 결과·과금 확정은 거부한다.
- 채널별 활성 실행기를 하나로 제한한다. 중복 start 요청은 새 OBS 송출·새 컵·새 차감을 만들지 않는다.
- 메모리뿐 아니라 DB에 broadcast/cup/bout ID, pairing, seed, 결과, 송출 구간을 저장한다. 재시작하면 기존 작업을 먼저 복구한다.
- 브라우저 결과 미확정 경기는 동일 pairing/seed/version으로 재실행할 수 있으나 논리 작업·과금은 한 건이다. 사용자나 관측자가 이미 본 경기의 재생 가능성은 복구 기록에 남긴다.
- 단말 절전과 브라우저 숨김을 방지하고, 실제 렌더링 진행·프레임 신선도·경기 진행을 관측한다. 프로세스 생존이나 RTMP 연결만으로 정상 방송이라고 판정하지 않는다.
- 송출 분의 성공은 인코더 송신·화면 진행과 Twitch 수신 상태의 관측을 함께 사용한다. 관측 불명 구간은 정상으로 추정 청구하지 않고 보류/면제한다. 재연결 전후 겹치는 구간은 합산하지 않는다.
- 중지·예산 고갈·승인 만료 시 새 작업을 막고 정해진 제한 시간 안에 종료한다. 이미 예약한 작업도 승인 종료시각을 무한히 넘어 실행하지 않는다.
- Twitch stream key와 실행기 credential은 호스트의 비밀 저장소에 둔다. 기존 Twitch 로그인 토큰의 메모리 전용 처리와 읽기 전용 채팅 계약은 유지한다.

방송 상태 예시: draft → awaiting_approval → queued → starting → running → stopping → completed. 예외는 paused_budget, recovering, needs_attention, failed, cancelled로 구분한다. 단순 timeout은 성공/실패 확정과 다르다.

운전 검증 순서는 3경기 컵 → 30분 실제 송출 → 2시간 및 장애 주입 → 24시간 실제 운전이다. 24시간 보고서에는 예정/실제 시작·종료, 실제 live 시간, 단절 구간, 렌더링 정지, 재시작, 완료/실패 컵, 가격표와 원장 합계를 기록한다. 시간이 24시간 흘렀다는 이유만으로 무중단 24시간 방송이라고 하지 않는다.

## 9. 리포트

서버가 수치를 계산하고 AI는 근거를 설명한다. 원본 snapshot과 schemaVersion을 저장해 다시 조회할 때 수치가 바뀌지 않게 한다.

- 계획: 채널, 목표 시간, 승인 예산, 허용 작업.
- 집행: 최초 잔액, 충전, 확정 지출, 반환/보정, 최종 잔액, 남은 예약액.
- 작업: 컵·경기 수, 사용 선수, 우승 결과, 실패·복구와 동일 요청 재시도 횟수.
- 방송: 실제 live 시간, 인코더·Twitch 관측 범위, 중단 구간, 화면 정지 여부.
- 에이전트: 어떤 선택에 재화를 사용했는지, 기존 선수를 선택한 이유, 다음 운영 제안.
- 증거: 내부 작업/원장 ID와 경기 링크. 공개 제출 자료에서는 비밀값·개인 계정 정보 제거.

시청자 수·동시 시청·채팅 참여는 실제 수집한 경우에만 단위·집계 방법과 함께 표시한다. 방송 시간이나 컵 수를 시청자 성과로 대체하지 않는다. 기본 리포트는 이미 저장된 결과를 재사용하고 조회마다 유료 모델 작업을 새로 만들지 않는다.

G0의 결제·송출 가능성 확인을 먼저 끝낸다. 이 경로가 막힌 상태에서 대시보드 장식을 진행하지 않는다. 11월 7일까지 P0 경로가 연결되지 않으면 P1을 전부 제외한다. 24시간 운전이 실패하면 축약 시연을 24시간 성공으로 표시하지 않는다. 새 24시간 검증을 끝낼 시간이 없으면 제출 설명에 미검증 범위를 명시한다.

작업 묶음은 저장소별 작은 PR로 나눈다. 대체로 G1/G2는 starter, G3는 양쪽 저장소의 계약 변경, G4/G5는 starter, G6 이후는 필요한 쪽만 수정한다. 서로 호환되는 계약 버전과 SHA를 함께 기록하고, 기능 완성 전 기존 공개 사용자의 기본 경로로 노출하지 않는다.

## 11. 검증 계획

| 영역 | 반드시 재현할 조건 |
| --- | --- |
| 결제 | 승인만 완료/취소/실패, capture 후 응답 유실, webhook 중복·역순·위조, 금액/통화/수취인 불일치 |
| 원장 | 동시 충전·동시 예약, 잔액 부족, 같은 key의 같은/다른 입력, 성공 후 재시도, 미확정 작업의 성급한 반환 방지 |
| 권한 | 다른 계정의 지갑/예산/채널 사용, 취소·만료된 승인, 모델이 가격·한도 변조, 시청자 메시지가 지출 지시 |
| 실행 | 두 worker가 같은 작업 claim, stale lease 결과, DB 저장 전후 crash, 브라우저 재탐색·iframe stale callback |
| 방송 | 연결만 살아 있고 화면 정지, 인코더 중단, Twitch offline/상태 미확인, 예산 고갈, 종료시각, 사용자 중지 |
| AI | 실제 MCP 도구 선택, 낮은 예산에서 가능한 편성, 모델 실패 시 지출 중단, 근거 없는 성공·성과 보고 방지 |
| 제출 | 공개 코드 새 설치, Sandbox 체험, 라이선스, 영문 설명, 비밀값 없는 로그, 24시간 증거와 실제 주장 일치 |

기존 실행 명령:

~~~sh
# oddbout-starter: 관련 기존 suite + 구현 시 새 suite 경로를 추가
node --test test/cloud-mcp.test.mjs test/account.test.mjs test/generations.test.mjs
npm run typecheck
npm test
# Edge import 경로를 변경하면 해당 함수에 대해서도 수행
deno check --frozen --config supabase/functions/ai-fighter-mcp/deno.json supabase/functions/ai-fighter-mcp/index.ts

# oddbout-twitch-cup: 실제 변경 영역의 focused tests 후 전체 검사
npm test -- test/twitch-tournament.test.ts test/twitch-arena-host.test.ts
npm run check
# 별도 터미널의 preview 서버가 필요함
npm run preview
npm run test:browser -- --seed=123
~~~

starter에서는 관련 테스트부터 실행하고 필요한 범위로 확장한다. PR 필수 CI가 통과해야 병합한다. 브라우저/호스트 시계를 바꾸면 기존 --raf-ms=1000 조건도 확인한다. 새 방송 모드·결제·DB·OBS 테스트는 위 기존 명령만으로 커버된다고 주장하지 않고 별도 suite와 실제 연동 기록을 추가한다.

문서만 바꾼 이번 작업은 코드 테스트 대신 링크·경로·명령 대조와 git diff --check로 검증한다. 구현 시험 결과와 이 계획의 목표를 혼동하지 않는다.

## 12. 배포와 심사자 실행

제출 README는 starter를 출발점으로 삼는다. Twitch Cup의 특정 SHA를 가져와 공개 에셋으로 빌드하고, 해커톤 콘솔·API·MCP·실행기를 시작하는 절차를 제공한다. 실제 명령은 구현 후 추가하고 새 checkout에서 실행한 결과를 기록한다. 비공개 게임 저장소, 개인 폴더, 기존 운영 credential을 요구하는 단계가 남아 있으면 독립 실행 완료로 보지 않는다.

기본 검증은 별도 Sandbox 앱과 테스트 DB에서 한다. 기존 운영 ai-fighter/ai-fighter-mcp·Render gateway·creator site와 배포를 구분한다. 운영 연결이 필요해지면 각 import graph와 배포 계획을 검토하고 기존 공식 배포 도구를 따른다. git push, PR 병합, DB migration, 서비스 배포, 실제 방송 시작은 각각 별개의 작업이다.

심사자에게는 무료 hosted demo와 공개 설치 절차를 제공한다. 채널 연결 없이도 짧은 대회와 Sandbox 충전/차감을 체험할 수 있게 하고, 실제 Twitch 송출 시연 및 24시간 증거와 구분한다. 필요한 테스트 접근은 제출 안내에서 안전하게 제공하고 공개 소스에 비밀키를 넣지 않는다. 공식 심사 종료 시점까지 실행 환경을 유지한다.

영상 구성 목표: 문제/방송 목표 20초 → PayPal 충전·잔액 30초 → 예산 승인·AI 비용 판단 35초 → 실제 대회·송출·차감 50초 → 실패 복구/리포트/24시간 증거 35초. 합계 170초를 목표로 하며 실제 촬영 후 3분 미만인지 확인한다. 기다리는 구간을 편집하면 편집 사실을 숨기지 않는다.
