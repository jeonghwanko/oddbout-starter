# Registration and revision

The skill body's hard rules win if this page disagrees. Stop and ask when the revision target is absent. Never call `enter_fighter` automatically. `idempotencyKey` stays with the bytes it names.

## Revise a registered fighter

`revise_hosted_motion` (`request_hosted_fighter` step `revise_motion`) only changes one motion of a legacy hosted job that is still at `motion_ready`. It does not edit a fighter that is already registered.

To change motions on a registered fighter, build a new local package and submit it with that fighter's id using `prepare_fighter_registration` `fighterId` by default. If this host cannot attach files, use `npm run fighter:register -- --dir <package> --fighter <id> --submit` only when the user explicitly chooses local registration and has a supported secure CLI login. A cloud-tool or auth failure alone does not authorize switching. This is a new submission. The `fighterId` stays. The previous submission is left as it was. A style-only edit with no new art is `update_fighter` kind `style`.

First read the returned fighter roster and confirm the requested target is present. If it is absent or ambiguous, stop and ask which fighter the user means. Never create or register a new fighter as a substitute for a missing revision target.

Read `get_profile`, then `get_my_fighters` view `list`. Report the account id and email returned by the profile and the count and limit returned in the list's `account` block. Missing fields (older servers) or a null limit stay unknown. The default of 3 is not a verified account limit. The profile nickname is always `ODDBOUT`. At the limit, a new fighter is `fighter-quota`. A revision of an existing fighter is not a new fighter.

Read `browse_oddbout` view `style_guide` before filling `combat.style`. There is no super clip: `super` is `slam`, `combo`, `fast` or `dash`. `temper` is an object of optional 1–5 grades (`guard`, `retreat`, `measure`, `patience`). `shockwave`, if present, must be `true`. Skill clip kinds are `stretch`, `pincer`, `flight`, `feint`, `slide`, `counter` and `brace`. The skill clip has no display-name field. The skill clip, a summon and a shockwave together are at most 2. `mix.fast` must be at most `mix.slam` + `mix.combo`.

New motion frames follow `docs/POSE-GENERATION.md`: right-facing side view, one scale based on standing body height 400 (not each pose's extent), and `https://oddbout.com/art/oddbout/style-anchor-front.webp` as the last reference. `inspect-motion` `needs-review` without a foot ROI is expected on action clips and does not block packaging. A `BORROWED_LANDMARK` warning means a landmark uses another clip's frame; prefer that clip's own frame. The warning does not fail validation.

## Final files and registration

Use native cloud `prepare_fighter_packaging` for packaging failures. It returns exact invocations of the workspace MCP tools `inspect_fighter_packaging` and `pack_fighter_package`. Execute them through the host's ordinary terminal tool using the returned JSON arguments, rather than asking the user to relay errors or hand-patch the kit. Cloud preparation does not read VM files and is not a successful package. A new reviewed kit can run separately against the existing workspace; keep the active runtime and selected originals.

When the user permits resolution optimization and the live contract lists `texture-resolution-1`, use `fitSheets: true` with kit 0.6.10 or newer. It fits sheet dimensions and total and per-asset byte and pixel budgets using actual measurements, keeps frames and timing, and preserves game size with `pixelScale`. It uniformly reduces density across normalized motions when totals need it, preserving the chosen encoding and originals. Read `report.budget`. The optional `outputScale` caps post-normalization density. A bounded worker may take up to ten minutes: resume the same host execution after its initial 30-second wait. Never silently shrink only a motion's character or remove frames. Required file, contract and upload limits still apply.

Quality diagnosis in `docs/GAIT-REVIEW.md` is optional later work. Preserve selected files and actual previews. No same-foot stance, visual verdict or numerical pass is required for packaging or registration. For GPT walk and run, use the kit CLI and the pinned sprite-gen-agent motion engine. Generate diagnostic key poses first. Review both physical legs, their hip attachments, contacts and body continuity before binding that image. Full sequences require the actual phase guide and reviewed key-pose reference, not only a layout guide. Use painted extraction with `ground_frames: false` to retain source flight height. Generation OK is not motion approval. Do not repair failed gait by pasting a frozen torso over separate legs, and stop after two consecutive failures of the same anatomy or contact requirement. Preserve unknown attempts without retrying.

Use upstream `game-pack`, then `fighter:pack` with the default `reviewPolicy: files-only`. Only file and contract checks gate packaging and registration. Gait scores and visual quality verdicts are deferred. Do not require a passing report, an explicit visual override, or regeneration. Preserve existing diagnostics unchanged. Legacy `required` and `engine-loop` plans also use file checks only. Review-group user choices still apply. Never hand-assemble sheets or invent measurements. A format fixture is never a generated character.

Run the existing manifest and full-file validators. Record `package` with the manifest and every asset, and preserve the user's final preview feedback. `package-review` is an optional quality record, not a gate. The session requires current validated package bytes, not a quality verdict or generation authorization. The final `get_creation_session` must have no blockers before submission.

Use the connected ODDBOUT account for registration from either workspace by default. Verify `get_profile` matches the user's intended account and call the cloud `get_my_fighters` view `readiness`. A workspace readiness result does not verify that login. `npm run creation:preflight -- --purpose registration` checks the workspace side without asking for a generation subscription. Never copy a CLI session into the connector. If the user explicitly chooses local CLI registration because this host cannot attach package files, use only the user's own account and a supported secure login handoff. A missing or failing cloud tool or authentication alone does not authorize that switch. Dry-run needs no login. The CLI prints `next` and `say`. A dummy run's `next` keeps `--dummy` and the loopback origin. Do not ask for callback URLs or tokens in chat, and report an authentication blocker if no secure handoff is available.

Read the cloud tools' current schemas, then call `prepare_fighter_registration` with the actual approved manifest, `upload_fighter_asset` for each `missingAssets` id (or each `assets` id when `missingAssets` is absent), `submit_fighter_registration`, and `get_my_fighters` view `submission`. `pending` and `pendingStages` are pipeline stage names, never asset ids. When the user explicitly chooses local registration on a host that cannot attach files, use `npm run fighter:register -- --dir <package>` for the login-free dry run, then the same command with `--submit` only after the user's registration request and secure CLI login. Never switch to it merely because cloud registration or auth failed. Pass actual host attachments and files, not rendered previews, made-up URLs, or paths on another machine. Materialize supported Library files with their original bytes and verify hashes.

Preserve the submission ID and idempotency key across identical retries. Inspect status before retrying an unknown response. Changed package bytes need a new key. A metadata-only final edit followed by an explicit registration request requires fresh validation, not repeated approval of unchanged animations. Then upload the approved front and expression sheet as his profile set ([front](front.md) step 6).

Report registration only after the response confirms it. A registered fighter starts in production (제작 중): it stays out of other people's cups, ranked duels and lists. Tell the user to check each required motion on the fighter page's All motions and enter it there. Call `enter_fighter` only on the user's request after showing every required motion and hearing each confirmed. If the connector or attachment route is missing, preserve the completed package and report that blocker. Do not silently switch registration accounts.
